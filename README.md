# Weather Intelligence API

A FastAPI service that forecasts two weather-derived indices for Sydney,
Australia, using machine learning models trained on historical data from the
[Open-Meteo Historical Weather API](https://open-meteo.com/en/docs/historical-weather-api).

## What it predicts

| Target | Type | Forecast | Output |
|---|---|---|---|
| Climate Comfort Index (CCI) | Regression | Next 3 days | Score from 0 to 100 (higher is more comfortable) |
| Weather Hazard Category (WHC) | Classification | Exactly 7 days ahead | Low, Moderate, High or Extreme Risk |

For each request, the API downloads the recent weather for Sydney leading up to
the requested date, builds the same features the models were trained on, and
returns the prediction.

## Endpoints

| Method | Endpoint | Description |
|---|---|---|
| GET | `/` | Project overview and list of endpoints |
| GET | `/health` | Health check |
| GET | `/predict/index/comfort_climate?date=YYYY-MM-DD` | CCI for the 3 days after `date` |
| GET | `/predict/category/weather_hazard?date=YYYY-MM-DD` | WHC for 7 days after `date` |
| GET | `/model-metadata` | Model details, features, feature importance and performance |
| GET | `/docs` | Interactive documentation (generated by FastAPI) |

### Example: Climate Comfort Index

```
GET /predict/index/comfort_climate?date=2025-01-01
```

```json
{
  "input_date": "2025-01-01",
  "predictions": {
    "comfort_climate": {
      "2025-01-02": 82.0,
      "2025-01-03": 78.7,
      "2025-01-04": 78.0
    }
  }
}
```

### Example: Weather Hazard Category

```
GET /predict/category/weather_hazard?date=2025-01-01
```

```json
{
  "input_date": "2025-01-01",
  "predictions": {
    "weather_hazard": {
      "2025-01-08": "Moderate Risk"
    }
  }
}
```

### Error handling

| Situation | Status code |
|---|---|
| Date not in `YYYY-MM-DD` format, or not a real date | `400` |
| Date in the future | `400` |
| `date` parameter missing | `422` |
| Open-Meteo weather service unreachable | `503` |
| Unknown endpoint | `404` |

Every error returns a JSON body with a `detail` message explaining the problem.

## Running locally

### Option 1: with Docker (recommended)

Requires [Docker Desktop](https://www.docker.com/products/docker-desktop/).

```bash
# Build the image
docker build -t weather-intelligence-api .

# Run it
docker run -p 8000:8000 weather-intelligence-api
```

Then open <http://localhost:8000/docs>.

### Option 2: with uv

Requires [uv](https://docs.astral.sh/uv/).

```bash
uv sync
uv run uvicorn app.main:app --reload
```

Then open <http://localhost:8000/docs>.

## Running the tests

```bash
uv run pytest
```

The tests cover every endpoint and each error case. The prediction tests call
the live Open-Meteo API, so they need an internet connection.

## Deployment on Render

The API is deployed on [Render](https://render.com) as a Docker web service.

1. Push this repository to GitHub.
2. In Render, choose **New → Web Service** and connect the GitHub repository.
3. Render detects the `Dockerfile` automatically. Select the **Free** instance type.
4. Click **Deploy**. Render builds the image and starts the service.

Render supplies the port through the `PORT` environment variable, which the
`Dockerfile` passes to the server. No other configuration is needed.

**Note on the free tier:** Render's free services go to sleep after 15 minutes
without traffic. The first request after that takes around a minute while the
service wakes up; later requests are fast. If a request appears to hang, please
wait and try again.

## Limitations

- The Weather Hazard Category model is **experimental**. High and Extreme Risk
  days are rare in Sydney and are not reliably detected by the current model.
  It should not be used for safety decisions. See `/model-metadata` for
  per-class performance.
- Predictions depend on the Open-Meteo API being available.
- The models assume a prediction for a date is made once that day is complete,
  because the features include that day's full 24 hours of weather. If the API
  is called with **today's** date, Open-Meteo supplies the hours that have not
  happened yet from its forecast model, so the request still succeeds but uses
  partly estimated rather than fully observed weather. Requests for dates fully
  in the past use observations only, which matches how the models were trained.
